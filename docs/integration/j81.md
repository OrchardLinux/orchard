# iPad Air 2 (J81, J82)

The iPad Air 2 support comes from Martin Puškáč's port (mattonik/ipad-nixos `b94d42f`), handed to Orchard by micro23 (micro23/ipadair2-omarchy `7ea2b2b`). The Orchard baseline described below runs from RAM only and does not include ANS1 installation support. A separate J81 contributor experiment later booted a full native ext4 root and verified persistence; see [follow-up results](j81-2026-10-29-followup/README.md). That experiment does not enable installation in this repository's shipped device profile.

| Model | Status |
|---|---|
| J81, iPad Air 2 Wi-Fi (`iPad5,3`) | Experimental. Display, Wi-Fi, battery, backlight and buttons seen working (section 3) |
| J82, iPad Air 2 Cellular (`iPad5,4`) | Untested. Differs from J81 in its Wi-Fi module (`rieslingb`) and the modem |

## 1. Boot it

You need the iPad in DFU mode, a Mac or Linux host with [uv](https://docs.astral.sh/uv/), Git, palera1n, libusb and a running native ARM64 Podman, and a Lightning cable. On macOS, keep the kernel cache on a case-sensitive filesystem: the kernel headers `xt_DSCP.h` and `xt_dscp.h` collide on case-insensitive APFS.

Orchard's own Pongo doesn't boot on the A8X yet: the device goes back to iPadOS instead of showing up in Pongo. Until that's fixed, boot with Hoolock's prebuilt Pongo:

```sh
curl -fL 'https://raw.githubusercontent.com/HoolockLinux/docs/23ebe1fbc375599221553a7e1815e5de182a6b42/binaries/Pongo.bin' -o Pongo-hoolock.bin
printf '%s  %s\n' '1e5543fd8e6dbd84c334b87d71aa473f4d347c2ba8a5e863b6e10f18461c7575' 'Pongo-hoolock.bin' | shasum -a 256 -c -
```

From an [omarchy-a](https://github.com/OrchardLinux/omarchy-a) checkout, put your Wi-Fi network in `examples/hardware-check/rootfs/etc/wpa_supplicant.conf` (WPA2; the file stays out of git, and the image carries it, so keep the image private):

```
network={
	ssid="your network"
	psk="your passphrase"
}
```

Then build and boot:

```sh
./orchard build examples/hardware-check --device j81 --modules --firmware --pongo "$PWD/Pongo-hoolock.bin"
./orchard run examples/hardware-check
screen /dev/cu.usbmodem* 115200          # Linux: screen /dev/ttyACM0 115200
```

When the Apple logo appears after `Checkmate!`, unplug and replug the cable at the iPad once, right away: the device has to come back in download mode within a few seconds.

The first build reads the Wi-Fi firmware from the iPadOS 15.8.8 IPSW, a few MB by byte range, and caches it. With `wpa_supplicant.conf` in the image, the Wi-Fi checks run at boot. `hardware-check` at the shell runs the rest in about three minutes; the results are in `/run/hardware-check.txt` and `/run/dmesg.txt`, also at `http://10.71.0.1:8080/` over USB networking.

`hardware-check keys` can report no events on a J81 even when the buttons work: it streams through `hexdump`, which loses buffered output when it is stopped. Capture raw events instead:

```sh
timeout 20 dd if=/dev/input/event0 of=/run/keys.bin bs=24
hexdump -v -e '24/1 "%02x " "\n"' /run/keys.bin | wc -l
```

## 2. What it consists of

- **Shared drivers, on main** (`kernel/patches/drivers/`): the A8X PCIe host as a T7000 variant of `apple-h9p`, with Martin's register sequence, Gen1 limit, DBI overrides, tunables and MSI layout as match data, and Wi-Fi power (REG_ON, device-wake) through `pci-pwrctrl-apple-wifi`; T7000 DART data; brcmfmac reading the BCM4350 OTP to pick the unit's Apple NVRAM; the D2207 PMIC GPIO for Wi-Fi REG_ON; the T7000 UART binding.
- **Device trees** (`kernel/patches/devices/t7001/`): UART5, the PCIe DART and PCIe controller on T7001; Wi-Fi and the battery gauge on the iPad Air 2. `brcm,board-type` is the ADT's Wi-Fi module: `rieslinga` on J81, `rieslingb` on J82.
- **Device data:** `devices/j81` and `devices/j82`, platform `apple-4k` (the A8X has no 16 KiB pages).
- **Firmware recipes:** the BCM4350 C2 firmware of each model's module from iPadOS 15.8.8, every NVRAM variant included.
- **m1n1:** unchanged. It fills the Wi-Fi MAC through the `wifi0` alias.

Every patch derived from Martin's work keeps him as author and names his original patches in its `[Orchard: …]` note.

## 4. Differences from Martin's port

A comparison against Martin's final state found every register value, mask, write order and delay on the PCIe path unchanged. These differ on purpose, and are where to look first if something breaks:

1. **DART leaf protection bits.** Orchard's leaves keep read/write permission bits; Martin's had none (`no_perms` in `apple_dart_hw_t7000`). Symptom if wrong: DART read or write faults when Wi-Fi starts.
2. **No double mapping.** Martin's runs mapped every DMA page twice (rebased and raw); Orchard maps once, rebased. Symptom if wrong: DART faults above 0x80000000.
3. **DART setup checks.** The translation setup reads back what it wrote and blocks DMA on a mismatch. Symptom: "translation setup … failed" or "blocking DMA".
4. **Device-wake timing.** pwrctrl raises device-wake before link training; Martin raised it after the link was up. Symptom: brcmfmac's firmware download or first command times out.
5. **OTP reading.** brcmfmac reads the BCM4350 OTP and sets its select bit, which Martin's path never did. Symptom: an OTP error, or an unexpected NVRAM name.
6. **Power domains.** The PCIe node holds all three PCIe power domains instead of leaving two to `pd_ignore_unused`. Symptom: no link.
7. **Firmware.** iPadOS 15.8.8's BCM4350 firmware is newer than the iOS 8.1 firmware of Martin's runs.

Not included in this baseline: storage (ANS1), touch, Bluetooth, the charger and audio. The later [external ANS1/native-root results](j81-2026-10-29-followup/NATIVE-ROOT.md) use a separately modified kernel and matching module, not the baseline tested in section 3. Touch was qualified later, on main's kernel ([section 5](#j81-hardware-run-on-main-2026-11-04)); the other listed peripherals remain unqualified.
Not taken from the port: storage (ANS1), the charger and audio. They weren't validated there and come later.

## 5. Touch (working on J81)

Martin's port reached the touch controller's SPI bus, not the touchscreen: his SPI3 node and the 60 MHz clock fix are integrated, and the rest comes from the iPad 5's N1 touchscreen, which the Air 2 shares. Every value has a source:

| Part | Source |
|---|---|
| SPI3 at `0x20a08c000`, IRQ 155, 60 MHz | Martin's patches 0008 and 0100; the ADT `spi3` node |
| SPI controller | The iPhone 6's T7000 support; the ADT describes both blocks alike (`spi-1,samsung`, version 1). It covers Martin's FIFO and word-delay fixes (0096, 0098) |
| Chip select 51, reset 82, interrupt 84, LDO enable 95 | ADT `spi3/multi-touch` functions |
| Analog supply: D2207 register `0x84` bit 2 (bits 0 and 1 shared) | ADT `pmuL(0x20e)`, decoded with iOS's D2207 LDO table; the same decoding gives the iPhone 6's working `0x85` bit 1 |
| Touch clock: PMGR `0x1e000`, 32768 Hz | ADT `KLCT` arguments and PMGR range identical to the iPhone 6's |
| Driver: the iPad 5's N1 runtime with `fll-mval` 6068 | iOS personality `C1F15,2` ("J82"): the same driver class, touch-size-id, parser and N1 defaults as the iPad 5's `C1F15,1`, whose `fll-mval` 6089 matches the iPad 5 entry |
| Display sync (GPIO 55) left alone | The ADT uses function code 2, unlike the iPad 5's code 3. The live iPadOS pad mode and waveform have not been measured. |
| Firmware: `z2fw-from-z2-packet@1`, `C1F15,2`, calibration at `0x10009000`, 1024 bytes | `J81.mtprops` (identical to `J82.mtprops`), the personality's `cal-dl-addr`, the ADT's `MtCl` size |

The inverted Y axis, taken from the iPad 5, is confirmed on J81 by the target test below.

### J81 runtime findings (2026-11-03)

On a J81 running stock iPadOS 15.8.5, `AppleMultitouchN1SPI` reports **family 22**, interface 1, a 40×30 sensor, firmware version `0x382`, region parameters `00 00 05 00 00 02` and a 14745×19657 surface. A separate Linux diagnostic using the 15.8.8 `0x382` firmware returned family 22 as well. The Air 2 match data previously expected family 21, which would reject this controller during discovery; the correction here removes that known mismatch. J82 has not been tested.

The diagnostic used an experimental SPI transport module, firmware upload and calibration sequence, and GPIO55 function 1 at the firmware's wake-to-dummy transition. Its first reads of region parameters and surface geometry were zero. Waiting six seconds before those reads returned the same nonzero values as iPadOS and let the input driver finish probe without a substituted descriptor or queue polling. Six seconds is an observed test delay, not a measured minimum or a production timing recommendation.

Touch still did not report: during two confirmed 30-second swipes after valid geometry, GPIO84's interrupt count did not increase and the input device emitted no events. A 100 ms wake-assisted reader found no queued contact frames in at least 600 reads. This points past the family mismatch and delayed descriptor toward scan or report generation; a missing interrupt alone does not explain the empty queue. The live iPadOS GPIO55 waveform is still unknown. The experimental transport and delay are not part of Orchard's shipped driver, and this patch does not qualify touch as working.

GPIO84 read `0x00070381` before the Linux probe and `0x0000038f` after module removal. In `pinctrl-apple-gpio`, IRQ startup selects group 0 and IRQ masking selects mode 7, accounting for the changed bits; the input data bit remained high. The released pad word is expected Linux IRQ state, not evidence that ATN is held low.

A later RAM boot with the bounded T7000 SPI path found a separate early probe failure: J81 has no display-sync pinctrl states, and `devm_pinctrl_get()` returned `-ENODEV`. A temporary module accepting this absent state and expecting family 22 completed probe and registered the touchscreen input device. During a confirmed 45-second swipe, `/dev/input/event1` produced 46 contact starts and 46 releases with changing X/Y coordinates, but each contact lasted about 10 ms: runtime `-EBADMSG` errors repeatedly triggered resynchronisation. A diagnostic capture showed that some 16-byte runtime replies put `e1` at byte 1 with a `00` or `01` leading byte; only the low checksum byte then fits in the transfer. A J81-specific parser change accepts this form when that byte matches the sum. With that change, a confirmed 30-second swipe produced 2,914 synchronized reports (about 97/s), 2,826 X updates and 2,861 Y updates, with no new frame errors. The combined changes have been tested as a temporary module on the exact #60 SPI kernel; a rebuilt Orchard image and desktop touch interaction remain to be tested.

### J81 hardware run on main (2026-11-04)

Touch works on main's own kernel. The kernel was main at `d214e53`, with no other patches: upstream `cee9395` (`kernel/upstream.lock`), all 417 patches of `kernel/series/apple-4k` applied with `git apply` in path order as `kernel/build` does, and `kernel/configs/apple-4k/config`, including `input/0015`-`0020` and `spi/0007`. It was built with GCC 15 through Nix ([`kernel/orchard-main.nix`](https://github.com/mattonik/ipad-nixos/blob/j81-touch-core/kernel/orchard-main.nix)), not in Orchard's clang-19 container, and `apple_z2` was loaded as a module. The touch firmware was the 15.8.8 `.z2fw` from `firmware.json` (SHA-256 `b9b4a072…`). The device booted from RAM through Hoolock's Pongo and m1n1, with an ipad-nixos initramfs rather than Orchard's `hardware-check` image. A small framebuffer test program ([`touchdemo`](https://github.com/mattonik/ipad-nixos/blob/j81-touch-core/docs/touchdemo.md)) drew the contacts on simpledrm.

- The driver probed and registered `iPad5,3 Touchscreen` (`/dev/input/event1`), with X `0..1535`, Y `0..2047` and 32 slots.
- Over 161 s of drawing: 6,843 reports, 99,850 events, 149 contacts, **five fingers at once**, 6,959 GPIO84 interrupts, and **no `touch frame error` or failed resynchronisation** in `dmesg`. The raw range seen was x `13..1535`, y `0..2018`.
- Orientation was checked with targets 96 px from two opposite corners. The mean reported position was off by dx -0.3, dy -7.5 px at top-left (15 samples) and dx -10.4, dy +8.9 px at bottom-right (10 samples), under 1.4 mm at about 10 px/mm. The owner saw each touch land in the middle of its target. No axis swap or flip is needed.

An earlier run that day used OrchardLinux/linux `df7c930` with the #57/#60 changes as local patches; the J81 header check was then an `of_device_is_compatible()` test rather than `shifted_reply_header`. It gave 2,462 reports and five fingers in 567 s, with two frame errors (`-74`/`-75`) that recovered on their own.

Not tested: J82, suspend and resume (`input/0020`), desktop interaction in an Orchard image, and the unit of `ABS_MT_TOUCH_MAJOR`.

## 6. Bluetooth controller (input and audio untested)

### J81 controller boot and scan (2026-11-02)

A J81 booted Bluetooth through the UART3 serdev child, the D2207 PMIC GPIO 2
power-enable and AP GPIO 164 wake line. `hci_bcm` loaded the privately supplied
patchram and reported the BCM4350 Riesling USI STC build 1529. A count-only
scan found 2 devices by classic inquiry and 29 LE advertisers in 20 seconds.

The test used the `wifi-touch-kmod-BT1` payload: Hoolock Linux 7.3.0-rc1 with
the J81 changes recorded in
[`mattonik/ipad-nixos` commit `c680f01`](https://github.com/mattonik/ipad-nixos/commit/c680f013bca09434f19c97f4edeb2a1537fa137b),
before that branch's patch renumbering. It was not Orchard's `hardware-check`
image or an exact build of Orchard `main`. The patchram was extracted locally
from iPadOS 15.8.8 and supplied from RAM; no firmware or capture logs are part
of this repository. The [public hardware note](https://github.com/mattonik/ipad-nixos/blob/8b3391687a3564d3bcb067b5930e3e5134144343/research/2026-11-02-bt-uart3-pinmux-lead.md#bt1-boot-result-2026-11-02-bluetooth-starts-by-itself)
records the run and its boundaries.

This confirms controller initialization and discovery on that tested payload.
It does not qualify Bluetooth input or audio on Orchard: pairing/connection,
keyboard or mouse input, audio, and Wi-Fi coexistence under load were not
tested. The device feature states remain `bluetooth_input = "untested"` and
`bluetooth_audio = "untested"`.
